Good afternoon. This is HomeGarden — my implementation of the Home Garden case.

I built it as a small production frontend rather than a CRUD exercise: Angular 22, on a backend that is slow and unreliable on purpose.

I'll show it in two parts. First the engineering — the stack, the architecture and the decisions behind them. Then the product, screen by screen. And we finish in the real app.

The domain is simple. Gardens, plants, a target humidity, and one business rule: the plants in a garden may never need more surface than the garden has.

The backend is the interesting part. Every response is delayed between two hundred milliseconds and two seconds, and one request in ten fails with a random 500.

Do nothing about that, and a screen that needs three requests breaks about a quarter of the time.

So the real brief, for me, was: make an unreliable backend feel calm and trustworthy — without ever lying about the data.

This is the stack, straight from package.json. The latest of each, and nothing that isn't used.

Angular 22, running zoneless — signals, deferred blocks and Signal Forms. NgRx SignalStore for state. Angular Material with the CDK, themed until it reads as a product.

Highcharts for the two charts, loaded only when they scroll into view. TypeScript 6 in its strictest settings. Nx holds the web app, the API and the end-to-end suite in one workspace.

Testing is Vitest and Playwright with axe. And the API itself is Fastify with zod — which matters, because the API's schemas become the client's types.

One note: the case suggested React. Angular was agreed up front, and the first ADR maps every concept for React readers.

eight cards, then the four pills

The architecture is five layers, and dependencies only point down.

Features are lazy routes. The shared UI kit is purely presentational. The stores own server state — they are the only thing that writes it. The domain is pure functions: the capacity rule, the humidity maths, the layout of the planner — no HTTP, no stores, not even text.

And core is the only code that knows the backend exists.

What I want to stress: this is not a diagram in a document. The boundaries are ESLint rules. Import a feature from the domain, and the build fails.

Every decision on this slide has an ADR — eleven of them in the repository.

the layers reveal top to bottom; the two green ones are the heart

Reactivity is signals all the way down.

The app runs without zone.js, so change detection happens only where a signal changed. Everything derived — used area, occupancy, humidity drift — is a computed, never stored where it could go stale.

State lives in three SignalStores with three scopes, written with the library's own idioms: withProps for collaborators, withLinkedState for state that resets with a key, signalMethod to follow the route. Every mutation returns a typed verdict, so a form can render a server error inline.

The forms are Signal Forms: the model is a signal and the rules are a schema — and the capacity rule is a validator that judges while you type, with the same function the server runs.

And the contract is one: the client's DTO types are inferred from the API's zod schemas. Change a field on the server, and the client stops compiling.

The flaky API is handled once, in one place, in four moves.

One: a stale-while-revalidate cache. A repeat visit renders instantly from memory, identical requests in flight collapse into one, and hovering a garden card already prefetches it.

Two: retry — but only when it is safe. Reads retry with backoff. Every POST carries an idempotency key, and the API replays a completed one from memory, so a lost answer can never create something twice.

Three: the races are closed by construction. Cache keys are per profile, stale answers are discarded by token, and a write always addresses the garden it targets. Switch profiles while the list is loading, and the wrong gardens never flash.

Four: pending is part of the design. Skeletons on reads, in-place ghosts on writes, an explicit retry when something really fails. There is no spinner anywhere — the build checks.

Performance is measured, and the CI keeps it honest.

The initial bundle is 381 kilobytes raw — down from 511 — after the shell's account menu became a deferred block; 107 kilobytes actually travel on a first load.

Every route is lazy; the planner and both charts ship in their own chunks behind placeholders of the same size, so nothing shifts when they arrive. Fonts are self-hosted and preloaded.

And two guards: budgets per chunk fail the build on regression, and a bundle check diffs every chunk against a committed baseline on every push — a chunk may grow three percent before someone has to say why.

the three numbers count up

Each layer of tests proves something different.

A thousand and forty-one unit and component tests, with a 95 percent gate on every axis — and nothing excluded to flatter the number.

Eighty-six Playwright tests in three projects: one against the real hostile API, one mocked for the states randomness can't guarantee, and one that boots the Dutch build.

Forty-three Storybook stories, each scanned by axe — a violation fails the run.

And zero of the things that make suites lie: no spinners, no sleep calls, no tests reaching into Material's DOM — Material is driven through the CDK harnesses.

All of it runs on every push, ending with a container image that is started and checked in both languages.

Three things that usually come last, done properly.

The stylesheet has an architecture: every colour, size and z-index is a token, and the dark theme is just a remap. Shared mixins for breakpoints, cards and zone colours; cascade layers so the foundations can never outrank a component; and the shared kit is named in BEM.

Two languages, compiled: one build per language, no translation runtime, no flash of the wrong text. Five hundred and seventeen messages, checked in CI, and the Dutch build has its own end-to-end project.

And accessibility that is tested, not declared: a skip link and a main landmark on every page, focus that follows navigation, the planner's beds as real focusable elements with the plan also available as a table, and axe on every screen in both themes.

That's the engineering. Now the product — welcome, dashboard, gardens, a garden and its planner.

Every screen was designed for the slow path as much as the happy one.

It starts on the welcome page. Profiles are cards — content-shaped ghosts while they load, never a spinner — and a new profile is created right here, with a friendly message if the email already exists.

Each profile sees its own gardens plus the shared ones. The session survives a refresh and is checked on boot.

Theme and language are chosen before signing in — light or dark, English or Dutch — and remembered.

What the screenshot shows: the first Tab reveals the skip link. Every page has one.

The dashboard answers one question first: which garden needs me?

The top line is the portfolio in one sentence — how many gardens are healthy, how many need attention, how many beds to water today. Then the KPI tiles.

The portfolio map places every planted garden by how full it is and how far its plants' humidity drifts from the target, with the attention rules drawn as bands. Choose a bubble, and that garden opens.

Below: the garden health grid with a small drawing of each garden, and Water today — which beds need water, by garden and watering zone, worked out from each plant's zone and planting date. With the outdoor humidity from Open-Meteo for gardens that have coordinates.

The gardens page is every plot at a glance.

Each card carries a capacity bar, a status chip and the plant count — and each card is enriched as its plants arrive, never with a fake zero.

Search and sort narrow the grid; the result count is announced to screen readers, which is what the screenshot shows.

Create, edit and delete are all here. A new garden appears as a ghost until the server confirms, and a deleted one comes back from the toast's Undo.

And every state is designed: loading, empty, an error with a retry, and no matches with a clear button.

A garden opens on its numbers: used, free, plants — and these stay ghosts until they are true, because the garden can arrive before its plants.

The gauge shows the average humidity the plants want against the garden's target, with the drift in words. Next to it, the outdoor reading.

Then the plan — we'll get to it — and the plants table: sortable, with edit and delete inline.

Under the table, the humidity profile: one column per plant, as wide as the space it takes and as tall as the humidity it wants. Choose a column, and the plant lights up on the plan.

The planner is the centre of the product: capacity you can see.

Every bed is drawn at its real square metres, so a 98-percent-full garden looks 98 percent full. That's a squarified treemap, a pure function of the plants — deterministic, so reopening a garden never rearranges it.

You can drag beds. They magnetise to the fence and to their neighbours, positions are saved per garden, and every move is undoable.

Layers tint each bed by its water needs and mark neighbours that clash. Group by water needs rearranges the whole garden in one step.

The timeline replays the garden day by day. The plan list is the same plan as a table — the text equivalent of the drawing. Expand fills the screen, with focus trapped like a dialog and Escape to leave. And any of these views saves as a PNG.

It is SVG, not a canvas engine: every bed is a real focusable element, which is what makes all of this accessible and testable.

Adding a plant starts with a catalog of twenty-seven common plants, ranked for this garden. Picking one only pre-fills the form.

Then Garden fit, live: available, this plant, remaining — the breakdown updates on every keystroke.

The screenshot is Antwerp Allotment, which is 95 percent full. A one-square-metre plant is refused while you type, before any request — and if you got past the form, the server would refuse it too.

It is one rule, one function: the same code runs in the form, in the store and on the server. And the verdict is tied to its field, so a screen reader hears it on the input.

This is the slow path, designed.

On a read: content-shaped ghosts that mirror the final layout line for line, so nothing moves when data lands. A fast answer never flashes one — there is a 150-millisecond grace.

On a write: the row you edited ghosts in place until the server confirms — you never wait behind a blocked screen.

On a failure: an honest state with a retry — never a stale screen pretending to be current. Transient failures are retried before you even see them.

One engine draws every loading surface, and under reduced motion the shimmer becomes a slow pulse.

The same product in Dutch — the same build, compiled in Dutch, with Dutch numbers and dates.

In the dark: a token remap, not a redesign. Every contrast pair was re-tuned per theme to pass AA.

And on a phone: the layouts hold from 375 to 1920 pixels. The end-to-end suite checks five widths for overflow, and runs axe in both themes.
