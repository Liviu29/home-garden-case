S01

HomeGarden

~30 sec

Hi, and thanks for having me. This is HomeGarden — my solution to the Home Garden engineering case.

In the next twenty minutes I want to show you two things: the product a user actually gets, and the engineering decisions behind it.

I'll cover the architecture, how state flows, how I dealt with a backend that is slow and unreliable on purpose, and how I tested it. Then a short live demo, and I'll close with the trade-offs and what I'd do next.

Let me start with the problem itself.

S02

The Challenge

~40 sec

The functional brief is compact. Users manage gardens and plants — full CRUD — and there's one real business rule: the plants in a garden can never need more surface than the garden has.

The interesting part is the backend. Every request gets between two hundred milliseconds and two seconds of extra latency, and one in ten requests fails with a random 500. That's intentional.

If you do nothing about it, a screen that needs three requests fails about twenty-seven percent of the time.

So for me, the real brief was: make an unreliable backend feel calm and trustworthy — without ever lying about the data.

Here's what I built on top of that.

Optional deeper answer — Why Angular, when the brief mentioned React?

The role is Angular-focused and I agreed the choice up front. Everything the case really evaluates — state, resilience, UX states, testing — is framework-agnostic. ADR-001 records the decision and includes a React concept map for reviewers.

S03

What I Built

~40 sec

At a high level, it's a small but complete product. You start on a welcome screen and pick or create a profile. The dashboard is a control center across all your gardens. You manage gardens and plants, with a catalog that recommends plants that actually fit.

The centerpiece is the Garden Planner — a visual, area-honest map of each garden.

Underneath everything there are two things users never see directly but always feel: the async experience — skeletons and ghosts instead of spinners — and a resilience layer that absorbs the backend's failures.

It's also keyboard accessible, works down to phone size, and has a full dark theme.

Before the architecture, a quick look at the stack — and what I left out.

S04

Technology Stack

~35 sec

This is the actual installed stack. Angular 22 with TypeScript, NgRx SignalStore for feature state, and RxJS only where streams genuinely help — the HTTP retry and one fan-out inside a store.

The UI is Angular Material 3 with my own token-based design system on top. Vitest covers units and components, Playwright covers end-to-end, including accessibility scans. It all lives in an Nx monorepo next to the provided Fastify backend.

What I'd like you to notice is what's not here: no extra state library, no query library, no canvas engine, no chart library. Every dependency had to earn its place.

Now, how it fits together.

Optional deeper answer — Why two TypeScript versions?

The app compiles with TypeScript 6.0. The root tooling stays on 5.9 because typescript-eslint's supported range doesn't include 6 yet. It's a deliberate, temporary split, documented in ADR-006, and the review lists it as an accepted trade-off.

Optional deeper answer — Why Angular 22?

It's the current major: zoneless by default, signal-based inputs and queries, linkedSignal, @defer and the new control flow are all stable. Starting a greenfield case on anything older would mean designing around APIs that are already being replaced.

S05

Architecture

~1 min 10 sec

This is the architecture from top to bottom, and the main rule is simple: dependencies only point down.

At the top are lazy routes and the shell, with a session guard that decides whether you land on the welcome screen. Below that are the feature screens. They never talk to HTTP directly — they read signals from stores and call intent methods.

The state layer has three SignalStores. One important decision here: plants have exactly one owner, the PlantsIndexStore. The dashboard, the gardens list and the detail page all read from it, so the same plant can never exist in two versions on screen.

Next to the stores sits the domain layer — plain TypeScript functions: the capacity rule, the planner layout, the recommendations. No Angular imports at all, so they're trivially testable.

Then data access: typed API classes and a small stale-while-revalidate cache with request deduplication. And at the bottom, one HTTP pipeline with a base-URL interceptor, a retry interceptor and a single error taxonomy.

Across the side are the shared pieces: design tokens, one skeleton engine, shared UI and global error handling.

That's the runtime view. Here's how it looks in the repository.

Optional deeper answer — Why no facade layer?

At this size the stores already are the facade: components call intents like createPlant and read signals. A separate facade per feature would add files without changing any dependency direction. If several teams consumed the same state, I'd add one.

S06

Project Structure

~35 sec

The repository is an Nx monorepo with three apps: the Angular web app, its Playwright suite, and the provided API.

Inside the web app there are three areas. Core holds app-wide singletons: the API clients, the session, the HTTP pipeline, the cache and error handling. Shared holds reusable UI and pure utilities — that's where the business rules live. Features are the routed screens, each owning its components and, where it needs one, its own store.

The boundary I care most about is the pure domain in shared utils. Those rules test in milliseconds, without TestBed, and any screen can reuse them.

Let me show how I used Angular 22 itself.

S07

The Angular 22 Approach

~45 sec

I didn't use new Angular APIs because they're new — each one solves a specific problem here.

The app is zoneless; that's the Angular 22 default, and zone.js isn't even installed. All twenty-eight components are OnPush and standalone, and dependencies come through inject(), so they're explicit.

The number I'm most happy with is this one: over a hundred computed signals and only two effects. I derive state instead of synchronising it. The two effects bridge to the outside world — loading when the route parameter changes, and setting the document title.

linkedSignal solves a nice problem in the planner: the camera re-fits when the panel resizes, but if you've zoomed in, it keeps your zoom.

And the planner sits behind @defer, so its code is its own lazy chunk, with a skeleton holding exactly its space.

The next step is how state itself is modelled.

Optional deeper answer — Why not httpResource everywhere?

The data layer needs things httpResource doesn't give me for free across stores: stale-while-revalidate, request deduplication, write-through after mutations, and race tokens. A small tested cache does that today. httpResource is a good fit for isolated reads, and moving to it later would be a local change, not a rewrite.

Optional deeper answer — Why not Signal Forms everywhere?

The forms need mature validation, cross-field rules like "coordinates together or not at all", and tight Material integration. Typed Reactive Forms give me all of that today, and I bridge form values into signals with toSignal where the UI needs them. Signal Forms is a clean migration path, not a missing feature.

Optional deeper answer — When would you use effect?

Only to push signal state into something that isn't a signal: the router-driven load, the document title, storage, a third-party widget. Never to copy one signal into another — that's what computed or linkedSignal are for. That's why there are only two.

S08

Signals & State

~1 min 10 sec

I split state into four kinds, because mixing them is where most bugs come from.

Source state is what the server told us: gardens, and plants per garden. It lives in SignalStores, and it only changes when the server confirms.

Derived state is everything I can compute from that: used area, free area, occupancy, humidity drift, the dashboard insights. I never store those. Utilization is computed from the garden plus its plants, so there's nothing to keep in sync and nothing that can go stale.

Local UI state stays local. The planner's camera, the active layers, the timeline, the table sort — those are component signals. The selected plant is shared between the map and the plant table through a two-way model binding, and it still never touches a store. That keeps transient interaction state out of the application state model.

Async state is explicit: a status per request, a saving flag that makes submits single-flight, and pending sets per entity that drive the ghosts.

The detail store is provided by the detail component, so it's created with the page and destroyed with it. And I chose SignalStore over classic NgRx because I wanted structure and testability without actions, reducers and effects for every interaction. At this scale, that ceremony wouldn't buy me anything.

The most important thing derived from that state is the capacity rule.

Optional deeper answer — What do you give up versus classic NgRx?

The global action log and time-travel devtools. If several teams shared this state, or we needed an audit trail of user intents, I'd reconsider. Here, stores as plain classes with patchState are easier to read and to test.

Optional deeper answer — Signals versus RxJS?

Signals for state — what the UI shows right now. RxJS for events over time where operators matter. In this app that's the HTTP retry with backoff and one rxMethod that fans out plant loads with distinctUntilChanged. Everything else is simpler as signals plus promises.

S09

The Capacity Rule

~55 sec

The business rule is: the total surface of a garden's plants can't exceed the garden's surface.

I implemented it exactly once, as a pure function, and it mirrors the server: the check is strictly greater-than, so a garden can be filled to exactly one hundred percent, just like the API allows.

When you edit a plant, the function excludes that plant's own current area. Otherwise, renaming a plant in a full garden would be rejected.

The same function feeds everything: the live meter in the plant dialog, the header, the planner, the dashboard, the capacity chip, even the recommendations.

The client check is about experience, not authority. The server still decides. If it rejects a request, that 400 maps to a functional error and the message lands inline in the form, with the user's input intact.

Which brings me to how the frontend talks to that server.

Optional deeper answer — How do you prevent capacity inconsistency?

Three layers. One pure function used by every screen, so the UI can't disagree with itself. The server as the authority, so two users racing each other can't overbook a garden. And server-confirmed state only — numbers change when the response arrives, not before. One gap I'd raise with the backend: PUT on a garden doesn't check shrinking below the planted area. The frontend warns about it; a server check is on my list.

S10

Backend Integration

~45 sec

Before designing anything, I measured the API. Sixty probe calls: a median of about one second, a p95 close to two seconds, and one in six failed. I used the Swagger docs and the Bruno collection to map the contract.

That investigation found quirks I now handle explicitly. Asking for the plants of a garden that doesn't exist returns 400, not 404 — so the garden request owns the not-found decision. Error bodies are normalised in one place. And a duplicate email on sign-up returns 409, which I turn into "continue as that profile" instead of a dead end.

I made one additive backend change: the garden's target humidity, with a migration, validation and a default, so existing data stays valid.

Every error maps to one of three kinds — technical, functional, or not found — and each kind has exactly one UX.

The latency shaped the frontend more than anything else. That's next.

Optional deeper answer — Why retry, and why retry writes?

With one failure in ten, retrying is what turns "one in four screens breaks" into practically never. The interceptor retries only 5xx and network errors — never 4xx — up to three times, with exponential backoff and full jitter. Retrying writes blindly is only safe here because this backend injects its failures before any handler runs, so a failed POST never created anything. In production I'd send idempotency keys and limit automatic retries to idempotent requests.

S11

Async UX: Why No Spinners

~1 min 10 sec

This is where the slow backend becomes interesting. Latency isn't the exception here — it's the normal case. So instead of putting a spinner in front of every operation, I made pending state part of the visual language.

Each verb gets its own feedback. A first load shows a skeleton shaped exactly like the content — and it only appears after a hundred and fifty milliseconds, so fast responses never flash. A refresh keeps the existing content readable while it revalidates. A create shows a ghost of the new item where it will land. An update grays out only that row, card or bed. And a delete keeps the item as a ghost until the server confirms. Nothing disappears before the server says so.

It's one skeleton engine, neutral gray, so a ghost never looks like real content. In the final review I measured every skeleton against the content it replaces, and they match within two pixels — so nothing jumps when data lands.

Accessibility is built in: loading regions are status regions with aria-busy, ghosts are hidden from assistive technology, and reduced motion swaps the shimmer for a gentle pulse. And spinners are banned by a check in CI.

Loading is only one state. Here are the others.

Optional deeper answer — Why skeletons rather than spinners?

A spinner says "wait" and hides everything. A skeleton says "this is what's coming", keeps your orientation and removes layout shift. For mutations, a localized ghost keeps the rest of the screen usable. The honesty rule: the ghost shows something is in flight; the numbers only change when the server confirms.

Optional deeper answer — How do you handle slow API responses?

Perceived speed and actual speed separately. Perceived: skeletons with an appear delay, localized ghosts, no blocking. Actual: a thirty-second fresh cache, shared in-flight requests, prefetch on hover, and lazy code. And correctness: late responses can't overwrite newer ones.

S12

Success, Empty, Error, Recovery

~35 sec

Every screen is designed for four states, not just the happy path.

Success is the normal content. Empty states are designed invitations — an empty garden tells you it has space to grow and offers to plant it. Errors are specific: a failure offers Try again, and an unknown garden gets a real not-found page instead of a skeleton that loads forever.

Recovery is mostly automatic. Retries absorb most failures and cached data stays on screen. When a mutation really fails, the ghost resolves back into the real item, with a toast and a retry action. A failed create keeps the dialog open with your input. And a transient 500 during the session check never signs you out — only a 404 does.

S13

Welcome & Dashboard

~30 sec

The welcome screen lets you pick a profile or create one inline. If the email already exists, it offers to continue as that profile.

The dashboard is designed to answer the user's main question quickly: which garden needs my attention? The KPIs summarise everything, the attention list is sorted by severity — full first, then nearly full, then humidity drift — and each garden gets a health card with a small botanical preview.

From there, into the gardens themselves.

S14

Garden Management

~25 sec

The gardens page is the management view. You can search by name or location, and sort by name, size or utilization — and it remembers your choice.

Creating a garden has sensible presets for size and humidity. While it saves, the button turns into a ghost; a deleted garden stays as a ghost until the server confirms. And hovering a card prefetches its data, so the detail page usually opens straight from cache.

Adding plants is where the product helps the most.

S15

The Plant Experience

~35 sec

The plant dialog starts with recommendations. There's a local catalog of twenty-seven plants, ranked for this specific garden: how close their humidity is to the garden's target, whether they fit the free space, and whether they're already planted.

One click pre-fills sensible defaults — but every field stays editable, so a custom plant is always possible. That cuts data entry without taking control away.

The Garden fit panel shows available, this plant, and remaining. Here it's blocking a plant that doesn't fit, before the server ever has to reject it.

The recommendations are product suggestions, not business truth. The capacity rule and the server still decide.

The feature that brings all of this together is the planner.

Optional deeper answer — Why a local catalog?

A runtime dependency on a third-party plant API would add another unreliable network hop to a product that already fights one. The catalog sits behind a provider interface, so an external source can plug in later without touching the dialog.

S16

Interactive Garden Planner

~1 min 10 sec

This is the Garden Planner, and it exists for one reason: square metres are abstract. "Nineteen and a half out of twenty" doesn't mean much as a number. The planner makes capacity spatial.

It's area-honest. Every bed's drawn area equals its real square metres, and the free soil is exactly the free area. So a garden that's ninety-eight percent full looks ninety-eight percent full.

You can explore it — pan, zoom, fit, fullscreen, layers, and a selection that stays in sync with the plant table.

You can arrange it — drag beds with magnetic edges and alignment guides, snap a bed back to its original spot, move beds with the keyboard, undo and redo — and it remembers your layout per garden.

And it helps you understand it: watering zones, a warning when neighbours need very different humidity, one-click grouping by water needs, and a timeline that replays how the garden was planted.

One boundary matters: positions are a visual preference. Moving a bed never changes capacity and never calls the backend.

Here's how it's built — and why I didn't use a canvas engine.

Optional deeper answer — Why localStorage for the visual layout?

The API has no coordinates, and positions are presentation, not domain data. The format is versioned, pruned to plants that still exist, and corrupt data falls back to the automatic layout. In a real product I'd persist layouts on the server per user, so they follow you across devices.

S17

Planner Architecture & Why SVG

~55 sec

The planner is a pipeline. Store state goes into a pure layout function — a squarified treemap — and it's deterministic: the same plants always give the same arrangement. Custom positions are applied on top, clamped inside the garden. That produces a view model — beds, soil, vegetation, labels, camera — and only then does Angular render SVG. The renderer never owns business state.

I evaluated Canvas and PixiJS. For this scale — tens of beds, not thousands of sprites — SVG wins. There's no rendering library at all: the entire planner chunk is about nineteen kilobytes over the wire. Beds are real, focusable elements with labels, so keyboard and screen readers work. Dark mode comes for free from CSS tokens, and I can test it with jsdom and Playwright selectors.

Rejecting a technology is a decision too. If this became thousands of animated entities, I'd reconsider WebGL — and because of the pure view model, only the renderer would change.

Enough slides — let me show it live.

Optional deeper answer — Why SVG instead of Canvas or Pixi?

Canvas gives you performance at scale, but you pay with accessibility, theming and testability, and with PixiJS roughly a hundred kilobytes of library before any app code. None of those costs buys anything at the size of a home garden. ADR-007 records the comparison, including a deferred 3D option.

S19

Performance

~40 sec

On performance, I separate two things that often get mixed up.

Perceived speed is what the skeletons and ghosts give you: the interface is understandable immediately, even when the backend takes two seconds.

Actual speed is about doing less work. The initial bundle is about a hundred and thirty kilobytes over the wire. Every route is lazy, the planner is a deferred chunk of about nineteen kilobytes, and profile editing only loads when you open it. Data stays fresh for thirty seconds, identical requests in flight are shared, and hovering a garden prefetches it.

To be transparent: the initial bundle sits just under its five-hundred-kilobyte raw warning budget, and the planner stylesheet is slightly over its twelve-kilobyte warning budget — still below the error limit, and on my list.

Speed only matters if everyone can use it.

Optional deeper answer — How do you prevent duplicate requests?

The cache stores the in-flight promise per key, so two components asking for the same garden at the same time share one request. Within thirty seconds a repeat read makes no request at all. And there's a Playwright test, request-ownership, that fails if a screen fires redundant GETs.

S20

Accessibility & Responsive

~40 sec

I targeted WCAG 2.2 AA. There's a skip link, a visible focus ring everywhere, and dialogs trap focus and give it back when they close. Tables are real tables, with sortable headers that announce their order.

The planner was the hardest part. Every bed is a keyboard-operable button, you can move a bed with the arrow keys as an alternative to dragging, and every move is announced. Reduced motion is respected everywhere — even the timeline won't auto-play.

It's responsive from phones to wide desktops — the planner's controls adapt to the size of the planner itself, not just the window — and the dark theme is built on the same tokens.

How do I know all of this actually works? Testing.

Optional deeper answer — How is accessibility verified?

Automated axe scans in both themes fail the suite on any serious or critical issue; the first run caught four accent colours below AA contrast, which I re-tuned. On top of that there are keyboard and focus-return tests, and the heading structure was audited screen by screen.

S21

Testing Strategy

~1 min 5 sec

The testing strategy follows risk, and each layer proves something different.

At the base are 815 Vitest tests in 59 files, plus 31 tests that boot the real API on an in-memory database. The pure domain tests cover the business rules: the capacity boundary, the edit self-exclusion, the planner layout and camera. Store and infrastructure tests cover the nasty async cases: a stale response can never overwrite a fresh one, three clicks produce one POST, and the retry never retries a 4xx. Component tests cover skeleton, data, empty and error states.

Then 67 Playwright tests run against a mocked network, plus six accessibility tests. Mocked on purpose: to test ghosts and recovery I need deterministic slowness and deterministic failures, and a random backend can't guarantee that.

Finally, six integration tests run the core flows against the real, flaky backend — that's what proves the contract.

Coverage is gated at ninety-five percent in the configuration. GitHub Actions runs all of it on every push: lint, typecheck, API and unit tests, the build, the no-spinner check, and both Playwright projects against their own database.

That leads to production readiness.

Optional deeper answer — How do you prevent race conditions?

Every load in the detail store takes a monotonic token; a response with an older token is dropped. The cache tracks write versions, so a local write during an in-flight fetch wins over that fetch's older response. Creates append idempotently, and deletes are guarded per entity so a double click can't fire twice.

S22

Production Readiness

~30 sec

The production build is AOT-compiled, optimized and content-hashed, with license extraction and no source maps — I verified there are zero map files in the output. Budgets are enforced for the initial bundle and for component styles.

There's a single API base URL in configuration, applied by an interceptor. Both environments use a relative /api path, so it deploys same-origin behind a reverse proxy, with an SPA fallback. There are no secrets in the repository. Security headers like CSP are documented, but not configured — that belongs to the hosting setup.

Which brings me to what I consciously left out — and what I'd add.

Optional deeper answer — How is the application production-ready?

Production build hygiene, budgets, a single configuration seam, a CI pipeline with a UX guardrail, documented deployment and caching, and a clear list of what's still needed for a real launch: authentication, idempotency, observability, security headers and end-to-end tests in CI.

S23

Trade-offs & What's Next

~50 sec

I want to be honest about the edges.

Some things I deliberately didn't build. No SSR — this is a signed-in management app with no SEO value. No classic NgRx, no query library, no WebGL engine — each would add weight without solving a problem I had. And no fake authentication pretending to be secure: there's a profile session, plus a documented design for the real thing.

In a real product, I'd add proper authentication — OIDC through a backend-for-frontend with an httpOnly cookie session. I'd add idempotency keys, so write retries are safe everywhere. I'd add paging and user scoping to the list endpoints, with ETags so revalidation is nearly free. I'd add observability and Web Vitals behind the existing logger seam, and store planner layouts on the server.

Let me wrap up.

Optional deeper answer — What would you change with another week?

Add idempotency keys and narrow the write retries, make the WebKit run a merge gate, and prototype server-side layouts. Then work with the backend on paging and user scoping.

S24

Questions

~25 sec

To summarise: HomeGarden is a complete product with a genuinely useful planner. Architecturally, it's layered, signal-driven and resilient against a backend that fails on purpose. And the judgment is in the details — one capacity rule, one owner per entity, derived instead of synchronised state, and honest pending states instead of spinners.

Thank you. I'm happy to go deeper into any of these decisions.

Backup Answers

Why Angular?

The role is Angular-focused and the choice was agreed up front. Angular gives me DI, routing, forms and a first-party testing story in one coherent framework, which suits a long-lived product.

It gives feature state a clear shape — state, computed, methods — as plain, testable classes, and it can be scoped to a component, so the detail store lives and dies with its page.

Actions, reducers and effects for every interaction would add ceremony without solving a problem here. I'd reconsider for shared multi-team state or an audit trail of intents.

Signals for current state; RxJS for time-based events where operators matter — the retry with backoff and one fan-out stream. Promises for one-shot requests.

To derive instead of store. Used area, free area and utilization are computed from the source, so nothing can drift out of sync.

Only to push state into a non-signal world: route-driven loading, the document title, storage. Never to copy signal to signal. There are two in the app.

Why not Signal Forms everywhere?

Typed Reactive Forms already cover validation, cross-field rules and Material integration. Signal Forms is a future migration, not a missing feature.

Why not httpResource everywhere?

I need SWR, deduplication, write-through and race tokens shared across stores. A small tested cache does that; httpResource could replace isolated reads later.

Why SVG instead of Canvas or Pixi?

How do you prevent duplicate requests?

A01

Request Lifecycle & Dependencies

Use this if someone asks "walk me through one request". A component reads a store signal; the route input triggers a load. The cache either answers from fresh data, answers and revalidates, or fetches. The API class goes through the interceptors — base URL, then retry — the DTO is mapped, the cache is written, and patchState updates the store. Computed values recalculate and the OnPush view renders. On failure, the error is classified once, and the store and the global handler react to that classification.

A02

Backend Behaviour

Latency is added in an onSend hook, uniformly between 200 and 2000 milliseconds. Failures are injected in an onRequest hook, ten percent, before any handler runs — which is exactly why retrying writes is safe here and only here. Both are always on; there is no environment flag. The failure maths: ten percent per request becomes about 0.01 percent with three retries.

A03

SignalStore Detail

GardensStore and PlantsIndexStore are root-level; GardenDetailStore is component-provided. The index is the single owner of plant entities, and the detail store exposes plants as a computed view of it. Writes are pessimistic with ghost UI; deletes leave only after confirmation. The one rxMethod fans out plant loads when the set of garden ids changes.

A04

Testing Matrix

Point at the row that matches the question. Pure rules and layout are Vitest; async correctness is store tests; slowness, failure and recovery are mocked Playwright; the real contract is the integration suite against the flaky API.

A05

Bundle & Performance Numbers

All numbers come from the final production build. Initial is 498 kilobytes raw, 132.8 transferred. The detail route is 37.2 kilobytes transferred and the deferred planner 19.4. The only budget warning is the planner stylesheet at 13.4 against a 12-kilobyte warning line.

A06

Production Roadmap

Three phases. Trust: real authentication, owner-scoped data, idempotency keys, security headers. Operate: error tracking and Web Vitals, and the WebKit run as a merge gate. Scale the product: paging and user scoping, ETag revalidation, server-side layouts, and an external plant catalog through the existing provider seam.
